# DGM · 项目解析

选父代、自修改、评测，形成多版本档案。

## 核心机制

候选是能运行的版本。档案允许从不同历史父代继续派生；这使一次退化仍能提供信息，并让开发者回到较早的分叉点。R1 的 registry 和物化目录已经承担其中两项职责。

## 原项目怎样运行

|环节|实现思路|使用条件或边界|
|---|---|---|
|定位与贡献|编码 Agent 的系统代码与工具|选父代、自修改、评测，形成多版本档案。|
|可修改对象|编码 Agent 的代码、工具和流程。|外层档案和父代选择在论文主设置中固定；不是重训基础模型。|
|如何发现问题|编码 Agent 分析评测日志、提出修改，再修改自身代码。|需要真实测试、可编辑代码和能恢复的父代状态。|
|父代与经验|概率选择倾向高表现，同时降低已产生较多有效后代的权重。|补丁及父子关系可恢复版本；失去基本编辑能力的候选不作为论文中的有效父代。|
|如何判断效果|代码任务测试；基础功能与更大评测分阶段进行。|论文单次 SWE-bench 配置成本高；编码结果不能直接外推 RAG。|

## 在 RAG-knowledge 中怎样试

以只保留末项的失败子代为父代，恢复对表头的选择。先验证 observation 属于这个父代的回执，再保存差分，恢复运行目录比对实际送达顺序。

## 接入时机与成本

优先复用。一次修正仍属于工程验证；生成更多代不等于改进更大。保留评测代码与候选源码的写入边界。
