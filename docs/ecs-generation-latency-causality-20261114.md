# 并行检索与生成耗时因果排查（2026-11-14）

结论：没有发现并行开关直接增加生成步骤或拖慢生成的代码路径。上一轮的生成耗时差异不足以证明因果；能确认的间接因素是提示引用排序/内容和输出长度发生变化，且相同实际请求也存在较大的远端响应时延波动。

## 统计口径校正

串行 b5 第2轮生成65.814秒影响算术均值。每题只有3次，两种统计方向相反，不应将其中任意一个当成并行的因果效果。旧报告已清楚使用中位数口径，但其结论只能描述本轮分布，不能证明并行导致生成变慢。

## 代码和30次实际时序

RAG_HYBRID_PARALLEL_ENABLED只出现在retrieval.py的执行分支选择。两路通过gather汇合，按固定向量/BM25身份处理结果，而不是按谁先完成决定引用顺序。生成模型绑定、temperature/max_tokens和stream参数不根据这个开关改变。

30次请求均为父子扩展结束→上下文构建结束→生成开始；上下文构建结束到生成开始间隔0.821–6.324ms。不存在同一请求的检索阶段和生成阶段重叠。ECS实际LLMService为每个服务实例创建AsyncOpenAI/httpx客户端，max_retries=0，不使用本地另一个provider池实现；不能把本地连接池能力当成已部署状态。

15组串并配对中12组的引用顺序/内容序列不同，3组完全相同。相同token数量不等于相同提示正文。真实初始向量和排名分数未全部保存，不能仅凭这些变化认定由异步完成顺序导致。

## 长度不是充分解释

- b7并行输出token三轮均多于串行，可能影响时长，但不是独立因果证明。
- b1-024第2轮输入都是15285 tokens，并行输出259少于串行262，仍18.929秒对8.482秒。
- b1-030第3轮引用顺序和内容相同、输入都是6828 tokens，并行输出205少于串行240，仍11.608秒对8.672秒；旧数据没有完整线级请求，因此不能宣称全部参数字节相同。

## 固定实际线级请求对照

独立侧进程调用正式generate_grounded_candidate代码；固定50条引用的原文与顺序、同一问题、模型、参数。完全不执行检索，不改正式API配置。四次SDK实际HTTP请求正文逐字节一致，SHA256 `efd41e88e4f68a29e6c6d6ce7621962e20a3260311fefa1b1a6806df8cce2969`。

请求/返回模型均为Qwen/Qwen3.5-4B，SiliconFlow；temperature=0.7，max_tokens=4096，stream=false，enable_thinking=false。每次新建HTTP客户端以接近当前正式实现，调用后关闭；授权头不记录。固定输入使用上轮b7的引用和问题，显式不附加运行时偏好策略，所以它是新的固定生成对照，不冒充旧30次全部实际线级提示。

这把主要波动定位到发出请求后等待供应商响应的区间；非流式接口不提供服务端排队、prefill和decoding的独立计时，不能再从ECS确定各自占比。该区间也包含网络往返，因此不能把全部时长严格等同于服务端排队。

## 可确认与不能确认

可确认：并行直接改变检索执行时序，提前进入后续阶段；生成输入依赖实际引用，引用排序/内容会影响答案；固定输入仍存在独立响应波动。不能确认：上述因素各自解释了上一轮多少毫秒，或并行本身导致生成变慢。当前证据不支持为此修改生产temperature、token上限或退回串行。

未改生产服务、未重启API、未变更默认模型或采样参数，API PID680975在实验前后相同。复用现有虚拟环境、模型绑定及已有选中引用；仅保留一个必要的固定请求正文和4次响应/HTTP时序，没有语料/索引/数据库副本。原始请求与回答、失败记录、冻结题集未修改。
